## 테스트 목표

SCAC QA는 개별 화면의 정상 동작뿐 아니라 다음 항목을 중점적으로 확인했습니다.

- 사용자 인증부터 결제, 이용권 발급, 좌석 입실과 퇴실까지의 전체 흐름
- 결제와 이용권·예약·사용 이력 간 데이터 일관성
- 스터디룸 예약 동시성 및 결제 대기 만료 정책
- 사용자와 관리자, `STAFF`와 `SUPER_ADMIN`의 권한 분리
- API 실패, 잘못된 입력, 중복 요청에 대한 안전한 예외 처리
- RTOS 명령 상태 전이와 장치 Health Check
- SOLAPI 알림 발송·실패 재시도·재시도 소진 처리
- 관리자 화면의 검색·필터·요약·페이지네이션 및 빈 데이터 처리

## 핵심 통합 테스트

### 전체 사용자 이용 흐름 — `TC-001`

```text
사용자 인증
  → 이용권 선택 및 결제
  → TicketUsage 발급
  → 좌석 선택 및 입실
  → 외출
  → 복귀
  → 퇴실
```

검증 항목:

- 단계별 화면 이동과 API 호출 성공
- 결제 완료 상태 저장
- 이용권 1건 발급
- 입실·외출·복귀·퇴실 상태 전이
- 좌석과 이용권 사용 상태 정리

### 스터디룸 결제 데이터 동기화 — `TC-078`

스터디룸 예약 결제 완료 후 다음 관계를 화면과 DB에서 확인했습니다.

```text
payment_table.reservation_id
meeting_room_reservation.payment_id
ticket_usage.reservation_id
```

기대 결과:

- Payment 상태가 `PAID`로 저장됨
- 예약 상태가 결제 완료 정책에 맞게 변경됨
- 결제·예약·사용 이력의 ID가 서로 일관되게 연결됨
- 동일 요청에 의해 데이터가 중복 생성되지 않음

### 스터디룸 동시 예약 방지 — `TC-083`

동일한 `roomId`, 예약 날짜, `startHour`, `endHour`로 두 요청을 거의 동시에 전송했습니다.

검증 결과:

- 두 요청 중 하나만 예약 성공
- 나머지 요청은 이미 예약 또는 결제 중인 시간으로 거부
- DB에 해당 시간대의 유효 예약이 한 건만 존재
- 비관적 락과 트랜잭션 내부 예약 가능 여부 재검증 확인

### 결제 요청 위·변조 차단 — `TC-081`

다음 비정상 요청을 Postman으로 검증했습니다.

- 실제 가격과 다른 금액 전달
- 비활성 이용권으로 결제 요청
- `ticketId`와 `reservationId` 동시 전달
- 두 결제 대상 모두 누락

잘못된 요청은 검증 오류로 거부하며 Payment, TicketUsage 및 예약 상태가 변경되지 않는지 확인했습니다.

### 결제 대기 예약 자동 취소 — `TC-070`

`PENDING_PAYMENT` 예약을 생성한 후 결제를 진행하지 않고 5분 이상 대기했습니다.

- 예약이 자동 취소 또는 만료 정책에 따라 정리됨
- 해당 스터디룸과 시간대가 다시 예약 가능한 상태로 복구됨

## 보안 및 권한 테스트

### JWT 만료·위조 — `TC-045`

Postman에서 만료된 Access Token과 서명을 변경한 Token으로 보호 API를 호출했습니다.

- 인증 오류로 요청 거부
- 보호 데이터 미노출
- 서버 데이터 변경 없음

### 타 사용자 데이터 접근 — `TC-020`, `TC-082`

사용자 B의 Token으로 사용자 A의 `paymentId`와 `reservationId`를 조회·취소하도록 요청했습니다.

- 타 사용자 결제·예약 접근 거부
- 소유자 정보 미노출
- 원본 결제와 예약 상태 유지

### 관리자 권한 — `TC-054`~`TC-065`

- `SUPER_ADMIN` 관리자 계정 페이지 접근 허용
- `STAFF`의 관리자 계정 화면 및 API 접근 차단
- 신규 관리자 계정의 기본 `STAFF` 역할 확인
- 마지막 `SUPER_ADMIN` 강등 차단
- 자기 자신인 `SUPER_ADMIN` 계정 삭제 차단
- 관리자 이름과 역할 Header 표시 확인

### 로그아웃 장애 복구 — `TC-077`

Chrome DevTools의 Network Request Blocking으로 로그아웃 API 요청 실패를 재현했습니다.

- 서버 로그아웃 요청이 실패해도 로컬 Token과 사용자 정보 제거
- 로그인 화면으로 이동
- 보호 화면에 인증 상태가 남지 않음
- 확인 Modal 및 처리 상태를 통해 중복 호출 방지

## RTOS 및 장치 테스트

### RTOS 명령 상태 전이

| TC       | 입력·상황                     | 기대 결과                          |
| -------- | ----------------------------- | ---------------------------------- |
| `TC-074` | 정상 장치 명령                | `PENDING → PROCESSING → COMPLETED` |
| `TC-075` | 지원하지 않거나 실패하는 명령 | `PENDING → PROCESSING → FAILED`    |
| `TC-076` | 완료된 명령에 finish 재요청   | 상태 유지 및 중복 후속 처리 차단   |

검증 방법:

- `POST /api/commands`로 명령 생성
- `GET /api/commands/pending`으로 RTOS 처리 시작
- `GET /api/commands/{id}`로 상태 확인
- `PATCH /api/commands/{id}/finish`로 결과 보고
- Backend DB와 RTOS Terminal 로그 비교

- 잘못된 요청으로 기존 장치 상태가 변경되지 않음

| `#21` | MEDIUM | 로그아웃 후 보호 기능 재접근 차단 실패               | 재검증 완료 |
| `#24` | MEDIUM | 동일 스터디룸 동시 예약 방지 실패                    | 재검증 완료 |

결함 처리 절차:

```text
REGISTERED → ANALYZING → FIXING → FIXED → VERIFIED
```

결함 수정 후 동일 테스트 케이스를 다시 수행하고 화면, API 응답 및 DB 상태를 함께 확인했습니다.

## Known Issues

### 완료된 RTOS 명령의 강제 상태 변경

정상 API 흐름에서는 `PROCESSING` 상태의 명령만 완료 또는 실패 처리할 수 있으며, 완료된 명령에 finish를 다시 요청하는 동작은 차단됩니다.

다만 DB에서 이미 `COMPLETED`인 `task_command`를 운영자가 수동으로 `PENDING`으로 되돌리면 RTOS Client가 해당 명령을 새로운 대기 명령으로 판단하여 실제 장치 작업을 다시 수행할 수 있습니다.

영향:

- 정상 사용자·RTOS API 흐름에서는 발생하지 않음
- DB 상태를 수동 변경하는 비정상 운영 상황에서 장치 작업이 중복 실행될 수 있음

향후 개선안:

- 별도의 처리 이력 또는 idempotency key 저장
- 완료된 `commandId` 재처리 차단 정책 강화
- 운영 환경에서 Command 상태 직접 변경 제한

### 실제 물리 장비 미연동

현재 카드 리더기, 영수증 프린터 및 출입문은 FreeRTOS POSIX 환경에서 시뮬레이션합니다. 따라서 실제 장치의 전원 장애, 종이 걸림 및 하드웨어 응답 지연 등은 테스트 범위에 포함하지 않았습니다.

## 테스트 수행 원칙

- 성공 응답만 확인하지 않고 화면, API 응답 및 DB 상태를 함께 검증했습니다.
- 중복 결제·예약·취소처럼 데이터 손상 가능성이 있는 흐름은 반복 요청을 포함해 확인했습니다.
- 인증·권한 테스트는 서로 다른 사용자와 관리자 역할을 사용했습니다.
- 실패 테스트 후 생성된 임시 데이터와 상태를 확인하고 다음 테스트에 영향을 주지 않도록 정리했습니다.
- 외부 결제와 문자 서비스는 Test 환경 및 수신 가능한 테스트 정보만 사용했습니다.
- 발견한 결함은 수정 완료만으로 종료하지 않고 동일 조건으로 재검증했습니다.
