## 문서 목적

이 문서는 SCAC가 구현해야 하는 기능과 품질 기준을 명확히 하고, 각 요구사항이 실제 화면·API·DB·QA 테스트로 구현되고 검증되었는지 추적하기 위해 작성했습니다.

주요 시스템 범위:

- 사용자 및 비회원 키오스크
- 관리자 웹 시스템
- Spring Boot REST API
- MySQL Database
- FreeRTOS POSIX 장치 Client
- Toss Payments 및 SOLAPI 외부 연동

### ID 체계

기존 DevProject Hub의 단계·분류 코드와 후반 통합 요구사항 ID를 유지합니다.

| Prefix | 의미                                 |
| ------ | ------------------------------------ |
| `FWD`  | React 화면 프로토타입 및 사용자 화면 |

| `LMIS` | Spring Boot·MySQL 및 관리자 시스템   |
| `RTOS` | RTOS 장치 이벤트 처리                |
| `SCAC` | 통합·보완 요구사항                   |

주요 분류 코드:

| Code    | 의미                     |
| ------- | ------------------------ |
| `AUTH`  | 회원·관리자 인증 및 권한 |

### 구분

| Type           | 설명                                       |
| -------------- | ------------------------------------------ |
| `FUNCTION`     | 사용자가 수행하거나 시스템이 처리하는 기능 |
| `NON_FUNCTION` | 성능·보안·안정성·사용성 등 품질 요구사항   |
| `UI`           | 화면 표시 및 사용자 인터페이스 요구사항    |

| `API`          | 외부 시스템 및 장치 연동 인터페이스        |

### 우선순위

| Priority | 설명                                            |
| -------- | ----------------------------------------------- |
| `HIGH`   | 핵심 서비스 흐름 또는 보안·데이터 정합성에 필수 |

- 로그인 후 JWT Access Token으로 보호 API에 접근합니다.

- 외출 시 시간권 사용을 일시 중지하고 복귀 시 다시 차감합니다.
- 퇴실 시 좌석을 `AVAILABLE`로 반환하고 종료 정보를 기록합니다.
- 중복 입실과 중복 퇴실 요청은 한 번만 반영합니다.

- 이용권 결제는 `ticketId`, 스터디룸 결제는 `reservationId`를 사용합니다.
- `ticketId`와 `reservationId`는 정확히 하나만 허용합니다.
- Backend가 이용권 가격 또는 예약 시간 기반 금액을 계산하여 요청 금액과 비교합니다.
- 비활성 이용권, 잘못된 대상 조합 및 위·변조 금액은 결제 생성 전에 차단합니다.
- 좌석 이용권 결제 완료 시 `READY` 상태의 `TicketUsage`를 발급합니다.
- 결제 완료만으로 좌석 입실을 자동 처리하지 않습니다.
- 결제 이력은 삭제보다 취소를 우선하고 취소 사유와 시각을 저장합니다.

- 동시 요청에는 비관적 락과 트랜잭션 내부 재검증을 적용합니다.
- 사용자는 본인 예약만 상세 조회하거나 결제 대기 취소를 할 수 있습니다.

- 관리자 결제 화면은 검색어·상태·수단·기간 필터와 요약 정보를 제공합니다.
- 시스템 로그는 행위자·대상·참조·상세 정보를 제공합니다.


- Backend가 `task_command`에 장치 명령을 생성합니다.
- RTOS가 대기 명령을 조회하면 `PROCESSING`으로 변경합니다.
- 정상 처리는 `COMPLETED`, 실패는 `FAILED`와 실패 사유로 저장합니다.
- `PROCESSING`이 아닌 명령에 대한 완료·실패 재요청은 거부합니다.
- 장치 명령 실패와 비즈니스 처리 실패를 구분하여 사용자 흐름이 불필요하게 중단되지 않도록 합니다.

Health Check 정책:

- RTOS는 5초 주기로 장치 상태를 Backend에 전달합니다.
- Backend는 장치 상태와 마지막 연결 시각 및 DeviceLog를 저장합니다.
- 20초 이상 Health Check가 수신되지 않으면 장치를 `OFFLINE`으로 변경합니다.
- 일시적인 네트워크 오류가 발생해도 RTOS Client는 종료하지 않고 다음 주기에 재시도합니다.

알림 정책:

- SOLAPI 발송 결과를 `notification_log`에 저장합니다.
- 실패 사유, 재시도 횟수, 외부 메시지 ID와 결과 코드를 기록합니다.

- 발송 성공은 `SUCCESS`, 최대 횟수 소진은 `RETRY_EXHAUSTED`로 처리합니다.
- 문자 발송 실패가 이용권 만료·퇴실 등 핵심 비즈니스 처리를 롤백하지 않도록 분리합니다.

- 사용자·관리자 행위와 장치 상태 변경을 기록합니다.
- 로그 유형, 중요도, 행위자, 대상, 참조 정보 및 상세 내용을 저장합니다.
- 조회 결과는 최신순으로 제공하고 관리자 화면에서 검색·필터할 수 있습니다.

## 핵심 인수 조건

프로젝트의 핵심 요구사항은 다음 조건을 만족할 때 완료로 판단합니다.

### 이용권 구매 및 좌석 이용

1. 사용자가 활성 이용권을 선택할 수 있습니다.
2. CARD Mock 또는 Toss Payments로 결제할 수 있습니다.
3. 결제 완료 후 이용권이 한 건만 발급됩니다.
4. 사용 가능한 좌석과 이용권을 검증한 후 입실할 수 있습니다.
5. 외출·복귀·퇴실 후 이용권과 좌석 상태가 일관되게 변경됩니다.

### 스터디룸 예약 및 결제

1. 날짜별 예약 가능한 시간을 조회할 수 있습니다.
2. 과거 시간과 중복 시간은 예약할 수 없습니다.
3. 임시 예약은 `PENDING_PAYMENT`로 생성됩니다.
4. 예약 시간과 시간당 금액으로 결제 금액을 검증합니다.
5. 결제 완료 시 Payment와 Reservation이 연결됩니다.
6. 5분 동안 결제되지 않은 예약은 자동 취소됩니다.
7. 동시 예약 요청에도 유효 예약은 한 건만 생성됩니다.

### 관리자 권한

1. `STAFF`와 `SUPER_ADMIN`이 일반 관리자 기능에 접근할 수 있습니다.
2. 관리자 계정 관리는 `SUPER_ADMIN`만 사용할 수 있습니다.
3. 일반 사용자와 `STAFF`의 권한 외 API 접근은 거부됩니다.
4. 관리자 작업과 상태 변경 결과가 시스템 로그에 기록됩니다.

### RTOS 장치 연동

1. 카드 리딩·영수증 출력·출입문 명령을 생성할 수 있습니다.
2. RTOS가 명령을 조회하고 성공·실패 결과를 반환합니다.
3. 명령 상태가 정의된 순서로 변경됩니다.
4. Health Check가 장치 상태와 마지막 연결 시각에 반영됩니다.
5. 통신 장애 후 다음 주기에 다시 연결을 시도합니다.

## 구현 범위 및 제한사항

- 카드 리더기, 영수증 프린터와 출입문은 실제 하드웨어 대신 FreeRTOS POSIX 환경에서 시뮬레이션합니다.
- Toss Payments와 SOLAPI는 교육·테스트 환경의 설정을 사용합니다.
- 시연 환경에서는 편의를 위해 실제 운영 환경보다 완화된 CORS 정책을 사용할 수 있습니다.
- 관리자 예약 기능은 조회·취소를 지원하며 별도의 예약 승인과 시간 변경 기능은 포함하지 않습니다.
- 완료된 RTOS 명령의 DB 상태를 운영자가 임의로 `PENDING`으로 되돌리는 비정상 상황에 대한 영속적 멱등성은 향후 개선 대상입니다.
- 성능 목표는 교육 프로젝트의 로컬·시연 환경을 기준으로 하며 별도의 대규모 부하 테스트는 포함하지 않습니다.
