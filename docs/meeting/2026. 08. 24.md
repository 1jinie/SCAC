## 💬 주요 논의 및 결정

### RTOS Command 저장 구조

- 기존 RTOS Command는 Spring 실행 중 메모리에만 저장되는 구조였음
- Server가 종료되거나 재시작될 경우 Command 처리내역이 모두 사라지는 한계 존재
- 최종 프로젝트에서는 장치 명령의 생성·처리 상태를 추적할 필요가 있다고 판단
- Command를 DB에 저장하여 요청 및 처리 결과를 영속적으로 관리하기로 결정
- `task_command` Table과 JPA Repository 기반 구조로 변경

### Command 처리 상태

- 기존 `PENDING / COMPLETED / FAILED`만으로는 RTOS가 실제 작업을 가져간 상태를 구분하기 어려움
- RTOS가 Command를 가져간 시점을 별도로 표현하기 위해 `PROCESSING` 상태 추가
- 최종 상태 Flow를 다음과 같이 구성

`PENDING → PROCESSING → COMPLETED / FAILED`

- RTOS가 Pending Command를 조회하는 시점에 Backend에서 `PROCESSING`으로 변경하도록 처리

### Device별 Command 구분

- 기존 Command에는 수행할 작업 종류만 있고 실제 대상 장치 정보가 명확하지 않았음
- Door·Card Reader·Printer 등 Command의 대상 장치를 식별할 수 있도록 `deviceId`를 추가
- Frontend에서 Command 생성 시 해당 장치의 Device ID를 함께 전달하기로 함

### 관리자 기간 검색

- System Log 및 결제내역은 데이터 누적 시 전체 목록만으로 확인하기 불편함
- 시작일·종료일을 이용한 기간 검색 기능을 제공하기로 결정
- 자주 사용하는 기간은 날짜를 직접 입력하지 않아도 되도록 `오늘`, `7일`, `이번달` Quick Button을 제공
