### 👤 이지현

### 스터디룸 예약 / 결제 / 관리자

#### Meeting Room Reservation / Payment

* 스터디룸 예약 결제 Frontend 연동 진행
* 기존 Frontend 중심의 예약정보 관리 구조 재설계
* 사용자가 선택한 스터디룸·예약일·시작시간·종료시간을 Backend 예약 API로 전달하도록 변경
* Backend에서 실제 `meeting_room_reservation` 데이터를 먼저 생성하도록 흐름 수정
* 예약 생성 후 반환된 `reservationId`를 Reservation Store에 저장
* 생성된 `reservationId`를 이후 결제 요청의 기준값으로 사용
* 좌석 이용권 결제와 스터디룸 예약 결제 흐름 분리
* 스터디룸 예약 결제 요청 시 `reservationId`, 예약 금액, 결제수단 전달
* 예약시간과 스터디룸 시간당 요금을 기준으로 결제금액 계산
* 카드 Mock 및 TossPay 결제 흐름에 스터디룸 예약 결제 연결
* 결제 완료 후 예약용 TicketUsage 발급 및 예약 상태 확정 흐름 연결

#### Reservation State

* 스터디룸 예약 생성 시 `PENDING_PAYMENT` 상태로 임시 예약 생성
* `PENDING_PAYMENT` 예약도 예약 중복 검사 대상에 포함
* 결제 진행 중인 시간대를 다른 사용자가 중복 예약하지 못하도록 처리
* 예약 가능 시간 조회에서도 `PENDING_PAYMENT` 상태 반영
* 결제 대기 상태에서 30분 이상 경과한 예약을 자동 `CANCELED` 처리하도록 Scheduler 보완
* 결제 완료 시 예약 상태를 `CONFIRMED`로 전환

#### Payment Result

* 결제 결과 조회 구조를 실제 Payment 데이터 기준으로 변경
* `ticketId` 존재 여부로 좌석 이용권 결제 판별
* `reservationId` 존재 여부로 스터디룸 예약 결제 판별
* 좌석 이용권 결제 결과와 스터디룸 예약 결제 결과 UI 분리
* `TicketPaymentResult` 컴포넌트 분리
* `ReservationPaymentResult` 컴포넌트 추가
* 스터디룸 결제 완료 화면에 예약일·이용시간·결제금액 표시
* 특정 예약 단건 조회 API 연동

#### Payment Cancel

* 스터디룸 예약 결제 취소 시 연결된 예약도 `CANCELED` 상태로 변경하도록 처리
* 결제와 예약 상태가 분리되어 남지 않도록 상태 연동 보완

#### Admin Payment

* 관리자 결제 목록에서 좌석 이용권과 스터디룸 예약 결제를 구분하여 표시

* 관리자 결제 상세 화면에 스터디룸 예약 정보 대응
* 결제 상품 유형에 `MEETING_ROOM` 표시 반영

## 💬 주요 논의 및 결정

### 스터디룸 예약·결제 데이터 구조 재설계

* 기존 스터디룸 예약은 선택한 방·날짜·시간 등의 정보를 Frontend Store에서 주로 관리하고 화면에서 데이터를 조합하여 다음 단계로 전달하는 구조였음
* 스터디룸 예약 결제를 안정적으로 연결하기 위해 실제 예약정보의 기준을 Backend의 `meeting_room_reservation` 데이터로 통일하기로 결정
* Frontend에서는 사용자가 선택한 스터디룸·예약일·시작시간·종료시간만 Backend로 전달
* Backend에서 실제 예약 데이터를 생성한 후 `reservationId`를 반환하도록 변경
* 반환된 `reservationId`를 Frontend Store에 저장하고 결제 생성·결제 결과 조회의 기준값으로 사용
* 예약정보와 결제정보를 Frontend 상태만으로 연결하지 않고 Backend에서 생성된 실제 예약 데이터를 기준으로 연결
* 스터디룸 예약 처리 흐름을 아래와 같이 정리

  * 예약정보 선택
  * `PENDING_PAYMENT` 임시 예약 생성
  * `reservationId` 반환
  * 결제 요청 생성
  * 결제 승인
  * 예약용 TicketUsage 발급
  * 예약 `CONFIRMED` 전환
* 결제 중인 예약시간도 다른 사용자가 선택할 수 없도록 `PENDING_PAYMENT`를 예약 점유 상태에 포함
* 일정 시간 내 결제를 완료하지 않은 임시 예약은 자동 취소하도록 처리

### 결제 취소 상태 연동

* 결제 취소 시 연결된 스터디룸 예약이 별도로 남지 않도록 예약 상태도 함께 `CANCELED` 처리
* 예약과 결제의 상태 정합성을 유지하는 방향으로 구조 보완
* 관리자 예약관리에서 예약을 먼저 취소했을 때 결제를 자동으로 취소하는 반대 방향의 처리 여부는 후속 흐름에서 추가 확인 필요

### RTOS 연동

* RTOS에서 Door 제어 및 장치 상태 전송 구조를 우선 구현
* Spring Backend 및 관리자 Frontend에서 해당 데이터를 처리하는 연동은 이후 작업으로 진행
