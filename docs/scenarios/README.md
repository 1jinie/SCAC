> 사용자, 관리자 및 RTOS Client가 SCAC의 주요 기능을 이용하는 흐름과 예외 상황을 정리한 문서입니다.

- 시나리오 관리: DevProject Hub
- 등록 시나리오: 22개
- 완료 시나리오: 22개
- 기준 브랜치: `main`
- 최종 수정일: 2026-08-31

## 시나리오 작성 기준

각 시나리오는 다음 항목으로 구성합니다.

| 항목             | 설명                                  |
| ---------------- | ------------------------------------- |
| Actor            | 기능을 시작하거나 처리하는 주체       |
| Pre-condition    | 시나리오를 시작하기 위해 필요한 상태  |
| Normal Flow      | 정상적인 처리 순서                    |
| Alternative Flow | 오류·취소·권한 부족 등 예외 흐름      |
| Post-condition   | 완료 후 시스템에 보장되어야 하는 상태 |
| Traceability     | 관련 요구사항·API·QA 테스트           |

## SCN-001 이용권 구매

| 항목           | 내용                                                          |
| -------------- | ------------------------------------------------------------- |
| Actor          | 회원 또는 비회원                                              |
| Pre-condition  | 판매 중인 이용권이 존재하고 Backend와 결제 서비스가 실행 중임 |
| Post-condition | 결제가 `PAID`가 되고 이용 가능한 `TicketUsage`가 한 건 발급됨 |
| 관련 요구사항  | `FWD-UI-004`, `LMIS-PAY-001`, `LMIS-PAY-005`, `SCAC-PAY-001`  |
| 관련 QA        | `TC-004`, `TC-016`~`TC-026`, `TC-081`                         |

### 기본 흐름

1. 사용자가 시간권 또는 기간권 목록을 조회합니다.
2. 이용권을 선택하고 결제수단을 선택합니다.
3. CARD 결제는 RTOS 카드 리딩 명령을 생성하고, Toss 결제는 Toss Payments 결제창을 호출합니다.
4. Backend가 이용권 활성 상태와 서버 기준 가격을 검증합니다.
5. 결제를 승인하고 Payment를 `PAID`로 저장합니다.
6. 선택한 이용권에 해당하는 `TicketUsage`를 한 건 발급합니다.
7. 결제 완료 화면을 표시하고 RTOS 영수증 출력 명령을 생성합니다.

### 예외 흐름

- 이용권을 선택하지 않으면 결제 화면으로 이동하지 않습니다.
- 비활성 이용권이나 변조된 금액은 Backend에서 거부합니다.
- 결제 실패·사용자 취소 시 이용권을 발급하지 않습니다.
- 성공 화면 새로고침 또는 연속 요청에도 결제 승인과 이용권 발급을 중복 처리하지 않습니다.

## SCN-002 입실 및 좌석 선택

| 항목           | 내용                                                        |
| -------------- | ----------------------------------------------------------- |
| Actor          | 회원 또는 입실 정보가 등록된 비회원                         |
| Pre-condition  | 사용 가능한 좌석 이용권을 보유하고 미입실 상태임            |
| Post-condition | 입실 기록이 생성되고 좌석과 이용권이 사용 중 상태가 됨      |
| 관련 요구사항  | `FWD-UI-002`, `FWD-UI-003`, `LMIS-ENTRY-001`, `KSD-DEV-002` |
| 관련 QA        | `TC-006`~`TC-008`, `TC-046`~`TC-048`                        |

### 기본 흐름

1. 사용자가 회원 또는 비회원 방식으로 입실 인증을 수행합니다.
2. 키오스크가 최신 좌석 목록과 상태를 조회합니다.
3. 사용자가 이용 가능한 좌석을 선택합니다.
4. Backend가 사용자, 이용권과 좌석 상태를 다시 검증합니다.
5. `check_inout`을 생성하고 TicketUsage를 사용 중으로 전환합니다.
6. 좌석 상태와 현재 사용자를 갱신합니다.
7. 출입문 개방 명령을 생성하고 완료 화면을 표시합니다.

### 예외 흐름

- 이용 가능한 이용권이 없으면 입실을 거부합니다.
- 사용 중·점검 중·비활성 좌석은 선택할 수 없습니다.
- 이미 입실한 사용자의 중복 입실을 차단합니다.
- 출입문 명령 실패는 입실 비즈니스 처리와 구분하여 기록합니다.

## SCN-003 퇴실 및 자리 반환

| 항목           | 내용                                             |
| -------------- | ------------------------------------------------ |
| Actor          | 현재 좌석 이용자                                 |
| Pre-condition  | 입실 또는 외출 상태의 이용 기록이 존재함         |
| Post-condition | 이용 기록이 종료되고 좌석이 `AVAILABLE`로 반환됨 |
| 관련 요구사항  | `LMIS-DEV-004`                                   |
| 관련 QA        | `TC-012`, `TC-013`, `TC-049`                     |

### 기본 흐름

1. 사용자가 퇴실을 요청합니다.
2. Backend가 현재 이용 중인 Checkin과 TicketUsage를 확인합니다.
3. 이용권 유형에 맞게 잔여시간과 종료 상태를 계산합니다.
4. `checkout_at`을 기록하고 좌석을 `AVAILABLE`로 변경합니다.
5. 출입문 개방 명령을 생성하고 퇴실 완료를 안내합니다.

### 예외 흐름

- 미입실 사용자의 퇴실 요청은 거부합니다.
- 중복 퇴실 요청은 상태를 다시 변경하지 않습니다.

## SCN-005 회원가입 및 SCN-006 로그인

| 항목           | 내용                                              |
| -------------- | ------------------------------------------------- |
| Actor          | 사용자                                            |
| Pre-condition  | 회원가입 시 사용 가능한 휴대전화 번호를 보유함    |
| Post-condition | 회원 계정이 생성되거나 JWT 인증 정보가 발급됨     |
| 관련 요구사항  | `LMIS-AUTH-006`, `LMIS-AUTH-007`, `LMIS-AUTH-002` |
| 관련 QA        | `TC-002`, `TC-036`~`TC-040`, `TC-045`, `TC-087`   |

### 회원가입 흐름

1. 사용자가 휴대전화 번호 인증을 요청합니다.
2. SOLAPI로 전송된 인증번호를 입력합니다.
3. Backend가 인증번호와 휴대전화 번호 중복 여부를 확인합니다.
4. 비밀번호와 입실 비밀번호 등 사용자 정보를 저장합니다.

### 로그인 흐름

1. 사용자가 휴대전화 번호와 비밀번호를 입력합니다.
2. Backend가 계정과 비밀번호 및 이용 정지 상태를 확인합니다.
3. Access Token과 Refresh Token을 발급합니다.
4. Frontend가 인증 정보를 저장하고 보호 화면에 접근합니다.
5. Access Token 만료 시 Refresh Token으로 재발급을 시도합니다.

### 예외 흐름

- 중복 휴대전화 번호는 회원가입을 거부합니다.
- 잘못된 비밀번호, 만료·위조 Token과 정지 회원의 접근을 차단합니다.
- 재발급 실패 시 인증 정보를 제거하고 로그인 화면으로 이동합니다.
- 키오스크 무입력 시간이 기준을 넘으면 사용자 상태를 초기화합니다.

## SCN-007 스터디룸 예약 및 결제

| 항목           | 내용                                                              |
| -------------- | ----------------------------------------------------------------- |
| Actor          | 로그인 회원                                                       |
| Pre-condition  | 예약 가능한 스터디룸과 미래 시간대가 존재함                       |
| Post-condition | Payment와 Reservation이 연결되고 예약이 확정됨                    |
| 관련 요구사항  | `SCAC-ROOM-001`, `SCAC-ROOM-002`, `SCAC-ROOM-004`, `SCAC-PAY-001` |
| 관련 QA        | `TC-050`, `TC-052`, `TC-078`, `TC-081`~`TC-083`                   |

### 기본 흐름

1. 사용자가 스터디룸 목록과 상세 정보를 조회합니다.
2. 날짜를 선택하고 예약 가능한 시간을 조회합니다.
3. 연속된 `startHour`, `endHour`를 선택합니다.
4. Backend가 소유자, 과거 시간과 중복 예약을 검증합니다.
5. `PENDING_PAYMENT` 상태의 임시 예약을 생성합니다.
6. `reservationId`를 대상으로 결제 주문을 생성합니다.
7. Backend가 `(endHour - startHour) × hourlyRate`로 결제 금액을 검증합니다.
8. 결제가 완료되면 Payment와 Reservation을 연결하고 예약을 확정합니다.

### 예외 흐름

- 과거 시간 또는 이미 예약·결제 중인 시간은 선택할 수 없습니다.
- 다른 사용자의 예약을 조회하거나 취소할 수 없습니다.
- 동시 요청에는 하나의 유효 예약만 생성합니다.
- 결제 실패 시 예약은 확정되지 않습니다.

## SCN-008 관리자 결제 취소 및 환불

| 항목           | 내용                                                           |
| -------------- | -------------------------------------------------------------- |
| Actor          | `STAFF`, `SUPER_ADMIN`                                         |
| Pre-condition  | 취소 가능한 완료 결제가 존재함                                 |
| Post-condition | Payment와 관련 이용권 또는 예약 상태가 취소 정책에 맞게 변경됨 |
| 관련 요구사항  | `LMIS-PAY-003`, `LMIS-PAY-004`                                 |
| 관련 QA        | `TC-071`, `TC-072`, `TC-079`, `TC-080`                         |

### 기본 흐름

1. 관리자가 조건을 적용해 결제 내역을 조회합니다.
2. 결제 상세에서 결제 대상과 상태를 확인합니다.
3. 취소 사유를 입력하고 취소를 요청합니다.
4. Backend가 결제 상태와 관리자 권한을 검증합니다.

### 예외 흐름

- 취소할 수 없는 상태이면 관련 데이터도 변경하지 않습니다.

## SCN-010 이용권 만료 및 자동 퇴실

| 항목           | 내용                                         |
| -------------- | -------------------------------------------- |
| Actor          | TicketUsage Scheduler                        |
| Pre-condition  | 종료 시각 또는 잔여시간이 만료 기준에 도달함 |
| Post-condition | 이용권과 입실 기록이 종료되고 좌석이 반환됨  |
| 관련 요구사항  | `LMIS-DEV-001`                               |
| 관련 QA        | `TC-014`, 만료 Scheduler 검증                |

1. Scheduler가 활성 TicketUsage를 조회합니다.
2. 만료 조건을 충족한 이용권을 종료 처리합니다.
3. 현재 좌석 이용이 있으면 Checkin을 종료하고 좌석을 반환합니다.
4. 다음 사용 가능한 이용권이 있으면 정책에 따라 자동 전환합니다.
5. 만료 예정 또는 완료 알림을 발송하고 결과를 기록합니다.

문자 발송 실패는 이용권 만료와 좌석 반환을 롤백하지 않습니다.

## SCN-011 RTOS 장치 명령 처리 및 장애 기록

| 항목           | 내용                                                       |
| -------------- | ---------------------------------------------------------- |
| Actor          | Spring Boot, RTOS Client                                   |
| Pre-condition  | Backend와 RTOS Client가 통신 가능하고 처리할 명령이 존재함 |
| Post-condition | 명령 결과와 장치 상태·로그가 Backend에 저장됨              |
| 관련 요구사항  | `SCAC-RTOS-001`, `LMIS-DEV-002`, `RTOS-DEV-004`            |
| 관련 QA        | `TC-066`~`TC-069`, `TC-074`~`TC-076`                       |

```text
PENDING → PROCESSING → COMPLETED
                     └→ FAILED
```

1. Backend가 장치 명령을 `PENDING`으로 생성합니다.
2. RTOS가 대기 명령을 조회하면 `PROCESSING`으로 변경됩니다.
3. RTOS가 명령 종류에 맞는 Handler를 실행합니다.
4. 성공 또는 실패 결과를 Backend에 보고합니다.
5. RTOS는 5초마다 장치 Health Check를 전송합니다.
6. Backend는 상태와 마지막 연결 시각 및 DeviceLog를 갱신합니다.

네트워크 오류가 발생하면 RTOS Client는 종료하지 않고 다음 주기에 다시 시도합니다. Health Check가 20초 이상 수신되지 않으면 장치를 `OFFLINE`으로 변경합니다.

## SCN-012·SCN-020·SCN-022 예약 상태 관리

### 사용자 결제 대기 취소 — `SCN-012`

- 사용자가 본인의 `PENDING_PAYMENT` 예약을 조회합니다.
- 소유권과 현재 상태를 확인한 후 예약을 취소합니다.
- 해당 시간대를 다시 예약 가능하게 해제합니다.

### 스터디룸 입실 및 이용 종료 — `SCN-020`

- 시작 시각이 된 확정 예약을 `IN_USE`로 변경합니다.
- 종료 시각이 지나면 `COMPLETED`로 변경합니다.
- 관리자와 사용자 화면에 최신 예약 상태를 반영합니다.

### 미결제 예약 자동취소 — `SCN-022`

- Scheduler가 생성 후 5분이 지난 `PENDING_PAYMENT` 예약을 조회합니다.
- 현재 상태를 다시 확인한 뒤 취소합니다.
- 이미 결제 완료 또는 취소된 예약은 변경하지 않습니다.

관련 요구사항: `SCAC-ROOM-003`, `SCAC-ROOM-005`  
관련 QA: `TC-070`, `TC-082`

## SCN-021 문자 알림 실패 재시도

| 항목           | 내용                                                    |
| -------------- | ------------------------------------------------------- |
| Actor          | Notification Scheduler, SOLAPI                          |
| Pre-condition  | `FAILED` 상태이며 재시도 가능 횟수가 남은 알림이 존재함 |
| Post-condition | 발송 성공 또는 재시도 소진 상태가 기록됨                |
| 관련 요구사항  | `SCAC-NOTI-001`                                         |
| 관련 QA        | `TC-073`, `TC-086`                                      |

1. Scheduler가 재시도 가능한 실패 알림을 조회합니다.
2. SOLAPI에 문자 발송을 다시 요청합니다.
3. 성공하면 `SUCCESS`와 외부 메시지 정보를 저장합니다.
4. 실패하면 실패 사유와 재시도 횟수를 갱신합니다.
5. 최대 실패 횟수에 도달하면 `RETRY_EXHAUSTED`로 변경합니다.
6. 소진된 알림은 이후 자동 발송 대상에서 제외합니다.
